# Reuse as a base for other targets

This repository (`figma-lp-generator`) is the **vanilla HTML/CSS/JS target** of the Figma → code
flow. The intent is to use it as a base for other future targets (WordPress/PHP, other frameworks) —
each target starts as a **fork/copy** of this repo (not a monorepo, not a submodule — decision
recorded on 2026-08-12). What changes between targets stays isolated; what is conceptual about
Figma/workflow/tooling stays the same, kept in sync manually as it evolves.

## Fork checklist for a new target

1. Copy the whole repo to a new directory/repo (`figma-wp-generator`, etc).
2. Copy without editing: `rules/core.md`, `rules/figma.md`, `rules/tooling.md` (change only the
   tooling cited), `scripts/compute-*.mjs`, `scripts/corrector-guard.mjs`.
3. Adapt (path/tooling, not the philosophy): `rules/assets.md`, `rules/validation.md`,
   `scripts/render-html-screenshot.mjs`, `.claude/skills/figma-analysis`,
   `.claude/skills/asset-management`, `.claude/hooks/*.mjs`.
4. Replace with the new stack's equivalent: `rules/html-css-js.md` + `responsive.md` + `media.md`,
   `scripts/schemas.mjs`, `.claude/skills/html-build` + `responsive-layout` + `lp-correction` +
   `visual-validation`, `.claude/skills/figma-to-html` (the whole pipeline + agents + references).
5. Update the `CLAUDE.md` Stack/Structure sections for the new target; keep Objective/Required workflow.
6. Run `npm run verify` (or the new stack's equivalent) before the fork's first commit.

## Do not do

- Do not promote this to a submodule/shared npm package while it is only 2-3 targets — YAGNI.
  Reconsider only if the core diverges between forks and the manual sync starts to really hurt.
- Do not mix targets inside the same repo (`targets/html-lp/`, `targets/wordpress-php/` in the same
  repository) — explicit decision to keep 1 repo per target, forked from this one.
